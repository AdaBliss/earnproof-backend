# Canonical request body hashes for sensitive mutations

High-risk mutations go through the approval queue (`src/approvals`) under
dual control: a requester proposes a payload, a different approver reviews
it, and execution runs later under a lease. The versioned payload hash is
the evidence that binds all three steps to the same reviewed payload.

## Scheme (version 1)

Implemented in `src/common/crypto/request-body-hash.ts`:

1. **Redact** — recursively strip fields whose key names a secret
   (`apiKey`, `password`, `privateKey`, `authToken`, `token`, `secret`,
   `credential`, `seedPhrase`, …; see `isSensitivePayloadKey`). The
   stripped key paths are reported as `redactedKeys`, so redaction is
   observable, never silent. Identifiers and reviewed parameters
   (`tokenId`, `amount`, `address`, `organizationId`) are *not* secrets
   and stay in the hash.
2. **Canonicalize** — key-sorted JSON with no whitespace (arrays keep
   their order, `-0` normalized to `0`). Same canonical form as
   `canonicalize()` in `src/common/crypto/canonicalize.ts`, plus bounds.
3. **Hash** — lowercase hex SHA-256 of the canonical UTF-8 bytes. The
   stored `ApprovalRequest.payloadHash` keeps its existing bare-hex
   format; the scheme version lives in `ApprovalRequest.payloadHashVersion`
   (default `1`).

Why secrets are stripped from the *hash input*: a hash of a low-entropy
secret is brute-forceable, so hashing a secret verbatim does not exclude
it. The raw payload is still stored as before — execution reads the
stored payload — only the hash input excludes secrets.

## Bounds (fail closed, never truncate silently)

- Maximum nesting depth: 32 (`MAX_REQUEST_BODY_HASH_DEPTH`).
- Maximum canonical length: 1 MiB (`MAX_REQUEST_BODY_CANONICAL_BYTES`).
- Non-finite numbers, bigints, functions, symbols, and circular
  structures are rejected (`UncanonicalizableRequestBodyError`).

An oversized or uncanonicalizable payload at request time is a `400`
(`BadRequestException`), not a `500`.

## Where the hash is recorded and checked

| Step | Behaviour |
| --- | --- |
| `ApprovalsService.create` | Stores `payloadHash` + `payloadHashVersion`; audit `approval.requested` carries both plus `redactedKeys`. |
| `approve` / `reject` | Fails closed on an unknown stored version (`ConflictException`); requires `expectedPayloadHash` to match exactly; audit `approval.approved` / `approval.rejected` carries the versioned hash. |
| `cancel` | Audit `approval.cancelled` carries the versioned hash. |
| `claimForExecution` | Re-hashes the stored payload before granting the lease and refuses the claim if it no longer matches the approved hash, or its version is unknown. This is what binds execution to the reviewed payload. |
| `completeExecution` | Audit `approval.executed` (actor `System`) carries the versioned hash. Written once, on the actual transition — the idempotent repeat path writes nothing. |

Authorization is unchanged: self-approval is still blocked, cancellation
is still requester-or-admin, and the decision/execution races keep their
existing conditional-update guarantees.

## Unknown versions fail closed

`verifyRequestBodyHash` throws `UnsupportedPayloadHashVersionError` for
any version outside `SUPPORTED_PAYLOAD_HASH_VERSIONS` (today: `[1]`),
and the service maps that to a `409 Conflict`. When the scheme evolves,
bump `CURRENT_PAYLOAD_HASH_VERSION`, add a branch, and keep verifying old
rows under their recorded version — never reinterpret them under the new
one.

## Pre-redaction rows

Rows written before redaction existed hashed the raw payload. Their
stored hash is still accepted at claim time via the legacy unredacted
form (`verifyRequestBodyHash(..., { allowLegacyUnredacted: true })`),
so requests approved before this change keep executing. New rows always
use the redacted form; the legacy path is only for re-verifying stored
rows, never for creating a hash.

## Cross-runtime reproducibility

The canonical form is plain JSON with sorted keys and no whitespace, so
any runtime can reproduce it. Golden vectors generated by an independent
Python implementation live in
`src/common/crypto/testdata/request-body-hash-vectors.v1.json`
(generator: `scripts/generate-request-body-hash-vectors.py`, stdlib
only) and are asserted in `src/common/crypto/request-body-hash.spec.ts`.
Regenerate after any v1 change with:

```bash
python3 scripts/generate-request-body-hash-vectors.py
```

Values whose JSON spelling differs between runtimes (`-0`, integers
above 2^53, non-finite numbers) are deliberately excluded from the
vectors and covered by Node-only tests instead.

## Migration

`20261219000000_add_approval_payload_hash_version` adds
`ApprovalRequest.payloadHashVersion INTEGER NOT NULL DEFAULT 1`.
Pre-existing rows were hashed with the version-1 scheme, so the
backfilled default keeps them verifiable. Applying the migration to a
live database needs CI/staging — it was not validated against a live
database in the sandbox (no Postgres available).
